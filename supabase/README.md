# supabase/

Single source of truth for the database schema. Shared by the portal and the mobile app (`../../impulsa360-mobile`).

## Layout

- `migrations/`: versioned migrations. First file is the prod baseline dump.
- `MODELO.md`: domain glossary and rules the code does not state. `EXPAND_CONTRACT.md`: deprecated objects still kept for installed app builds.
- `config.toml`: CLI config as generated by `supabase init`. No secrets.

## Commands

```
set -a; source .env.dev; set +a                # or .env for prod
supabase migration new <name>                  # create file (never name it by hand)
supabase db push --dry-run --db-url "$DB_URL"  # list pending migrations
supabase db push --db-url "$DB_URL"            # apply pending migrations
node scripts/restaurar-respaldo-en-dev.mjs     # DEV = latest prod backup, PII replaced, at the backup's schema version
supabase migration list --db-url "$DB_URL"     # migration history of the loaded env
```

Testing a migration on real data: restore the backup in DEV → `db push` → check with `psql`. To roll DEV back, restore again.

## Rules

- Never edit an applied migration. Add a new one.
- Never change schema in the SQL Editor.
- Prod pushes need explicit approval.
- Deploy DB before apps. Keep changes backward compatible with every mobile build in the field.
- Expand/contract: add the new column or function, ship both apps, drop the old one only after the oldest supported build stops using it.
- Enable RLS on every table in `public`. Keep `security definer` functions to a minimum, with `set search_path = ''`.
- No data in migrations except reference data.
- Every new table, sequence or function declares its own grants in its migration; default privileges give `anon`/`authenticated` nothing.
- Touching code that reads or writes the DB: check `EXPAND_CONTRACT.md`. Remove rows whose condition is met; add a row when your change leaves something unused.
